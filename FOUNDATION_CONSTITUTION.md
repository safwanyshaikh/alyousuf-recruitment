## 1. FOUNDATION CONSTITUTION (principles)

1. **Six entities, one hierarchy, no exceptions:**
   `Client → Project → Campaign → Requirement → Associate → Candidate`.
2. **One schema per entity.** The repo and live sheet currently disagree (Phase 0
   evidence). This Constitution is the single authoritative schema. All drift
   reconciles to it.
3. **Truth is manual.** Foundation fields are entered by recruiters or generated by
   the system (IDs, timestamps, counters). No Foundation field is authored by AI.
4. **Identity by ID, never by name.** Every entity has a system primary key (PK).
   Names are denormalized display only and are never join keys.
5. **No orphans.** Every child entity carries a mandatory foreign key (FK) to its
   parent. A Requirement without a Campaign cannot exist (Section 6).
6. **No FK in free text.** Foreign keys live in dedicated columns, never inside Notes
   or any narrative field.
7. **Intelligence is separate.** The Requirement (and every entity) master stays
   operational. All derived intelligence lives in the K14 layer, keyed by PK
   (Section 7).
8. **Status is governed.** Every entity has a controlled status vocabulary (Section 5).
9. **Additive reconciliation.** Locking this schema adds/renames columns and backfills;
   it never destroys live data.

## 4. FOREIGN KEY RULES

1. **Every FK is a dedicated ID column.** Never a name string, never inside Notes.
2. **Parents resolve by PK:**
   - Project.ClientID → Client.ClientID
   - Campaign.ClientID → Client.ClientID · Campaign.ProjectID → Project.ProjectID
   - Requirement.CampaignID → Campaign.CampaignID (**mandatory**) · Requirement.ProjectID → Project.ProjectID · Requirement.ClientID → Client.ClientID
   - Candidate.Source Associate → Associate.AssocId · Candidate.Source Campaign → Campaign.CampaignID
3. **Name columns are DEN (denormalized) and read-only mirrors.** If a parent renames,
   the DEN copy is refreshed from the FK; the FK never changes.
4. **No cascade delete.** Status change only (Section 5). Records are archived, never
   hard-deleted, preserving history (K14 Governance Lock).
5. **Migration of legacy FK-in-Notes:** the existing `[Project:PROJ-xxx]` strings in
   Requirement Notes are parsed out into ProjectID, and CampaignID is derived from the
   project's campaign. Notes returns to narrative-only.

## 5. STATUS GOVERNANCE

Each entity has ONE controlled status vocabulary. No free-text status.
| Entity | Allowed Status values |
|--------|-----------------------|
| Client | ACTIVE · INACTIVE · BLACKLISTED · PROSPECT |
| Project | ACTIVE · COMPLETED · CANCELLED · ON-HOLD |
| Campaign | ACTIVE · COMPLETED · CANCELLED · ON-HOLD |
| Requirement | OPEN · FILLED · CLOSED · ON-HOLD |
| Associate | ACTIVE · INACTIVE · BLACKLISTED |
| Candidate (State) | NEW · PARSED · INCOMPLETE_CONTACT · UNKNOWN_TRADE · FRESHER_POOL · UNDER_REVIEW · SHORTLISTED · CLIENT_SENT · CLIENT_SELECTED · OFFER_ISSUED · VISA_PROCESS · ECR_PENDING · MEDICAL_PENDING · READY_TO_DEPLOY · DEPLOYED · REJECTED · HOLD |

Rules:
- A recruiter-set terminal status (FILLED, CLOSED, BLACKLISTED, DEPLOYED) is **never
  auto-reverted** by any process (including K14).
- Candidate State transitions are forward-governed; OFFER→VISA→MEDICAL→DEPLOY is the
  mobilization spine read by Execution (Phase 3).

## 6. CAMPAIGN-MANDATORY RULE (locked)

> **No standalone Requirements.** Every Requirement MUST carry a non-null CampaignID.
> Creation flow is fixed and has no bypass:
> `Client → Project → Campaign → Requirement`.

- A Requirement cannot be created, imported, or saved without a resolved Campaign.
- The Campaign resolves (or is created) under a Project, which resolves under a Client.
- This eliminates orphan requirements and makes the hierarchy enforceable at write time.
- Today's violation (requirement linked to Project via a Notes string, no Campaign) is
  corrected by the FK migration in Section 4.5.

---

## 7. REQUIREMENT INTELLIGENCE SEPARATION RULE (locked)

> **The Requirement master is operational and recruiter-owned. It holds NO AI output.**

- The ONLY AI-touched field on the Requirement master is `Trade`, and only with
  `Trade Source = AI`; a recruiter override flips it to `Trade Source = Recruiter` and
  locks it.
- All derived intelligence — extracted skills, parsed qualifications, responsibilities,
  industry classification, requirement score, salary guidance, risk flags, match
  intelligence, confidence — lives in the **K14 layer, keyed by ReqID**, never in the
  Requirement master.
- This rule generalizes to every Foundation entity: Foundation stores truth; K14 stores
  intelligence about that truth. The two never share a column.
- Consistent with the K14 Governance Lock: legacy/AI engines are evidence and output,
  never promoted into the truth schema.

## 8. ASSOCIATE ARCHITECTURE (locked)

1. **Associate is a core Foundation entity**, positioned between the
   Campaign/Requirement layer and the Candidate leaf. GCC reality:
   `Requirement → Associate → Candidate`.
2. **Foundation stores associate IDENTITY** (Section 2.5): who they are, license,
   specialization, capacity, contact, status.
3. **Associate PERFORMANCE is NOT Foundation.** Rating, commitment accuracy,
   mobilization rate, total submissions/selections/mobilizations are **outcome
   intelligence** computed by K14 (`K14.OUTCOMES` → `K14.MEMORY`), evidenced today by
   the live `_AssociateReliability` and `_Commitments` tabs. Foundation links to the
   associate; K14 judges the associate.
4. **Every sourced candidate carries `Source Associate` (FK).** This makes every
   candidate traceable to its origin and feeds associate-performance learning.
5. **Commitments** (`_Commitments`: committed qty vs delivered, per requirement) are
   Execution/Outcome records (Phase 3), keyed by AssocId + ReqId — not Foundation
   master fields.
